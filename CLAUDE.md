# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Install dependencies
pip install -r requirements.txt

# Run development server (SQLite by default)
python manage.py runserver

# Apply migrations
python manage.py migrate

# Create a superuser
python manage.py createsuperuser

# Create and apply a new migration after model changes
python manage.py makemigrations
python manage.py migrate

# Run tests
python manage.py test core

# Collect static files (for production)
python manage.py collectstatic

# Docker Compose (production stack: PostgreSQL + MinIO + Traefik)
docker compose up -d
```

## Architecture

### App structure

Everything lives in a single Django app, `core`. There is no separate apps split — all models, views, services, and template tags are in `core/`.

- `core/models.py` — all ORM models
- `core/views.py` — all view functions (function-based views only)
- `core/urls.py` — all URL patterns (included from `config/urls.py`)
- `core/services/calculations.py` — financial calculation engine
- `core/services/payment_generator.py` — auto-generates `Payment` rows from `ReceiptDistribution`
- `core/services/reports.py` — P&L and accounting ledger report builders
- `core/templatetags/core_filters.py` — `|markdown` (bleach-sanitized) and `|pretty_json` filters
- `core/context_processors.py` — injects `APP_NAME` and `BRANDING` (AppSettings singleton) into every template

### Database

- **Dev**: SQLite (`db.sqlite3`) — the default when no `DATABASE_URL` or `DB_ENGINE` env var is set.
- **Production**: PostgreSQL via Docker Compose. Switched automatically by `config/settings.py` when `DATABASE_URL` or `DB_ENGINE=django.db.backends.postgresql` is present.
- **Media files**: Local filesystem in dev; S3-compatible MinIO when `AWS_S3_ENDPOINT_URL` env var is set.

### Financial data model and calculation flow

The core financial flow is:

1. **Job** has **SettingsVersion** (versioned platform-fee rules) and optional per-job overrides.
2. **Receipts** record money received per job.
3. When a receipt is created, `ReceiptDistribution` rows are written (immutable snapshots of how that receipt was split across workers at creation time). These are never recomputed from allocations; they are a permanent record.
4. `Payment` rows track actual payouts. When a receipt is saved, `generate_payments_from_receipt()` auto-creates pending `Payment` rows (one per worker distribution).
5. Worker totals (`earned`, `paid`, `due`) are computed in `compute_worker_totals()` by aggregating `ReceiptDistribution.computed_amount` and `Payment.amount_paid where is_paid=True`.
6. Finalizing a job writes a `JobCalculationSnapshot` (JSON blob of totals + per-allocation earned). Finalized jobs show snapshot data rather than live calculations, and block edits to receipts/allocations.

`SettingsVersion` records are immutable after creation — clone to modify. Each job stores its own `sett
ings_version_id` so calculations are always based on the rules that were active when the job was created.

### Role system

Three roles: `admin`, `worker`, `middleman`. Users hold roles via `UserRole` (many-to-many). The `User.active_role` field tracks which role is currently active for UI filtering (workers and middlemen can switch roles if they hold both).

- **Admin**: full access to everything.
- **Middleman**: sees only their own jobs (jobs they created or jobs where `Job.middleman` = their profile). Can manage workers and clients.
- **Worker**: sees only jobs they have an `JobAllocation` or `Payment` on. Cannot see other workers' contact info.

`get_visible_jobs(user)` in `views.py` is the central queryset filter — call it whenever you need to scope jobs to the current user.

Every non-admin user has both a `Worker` and a `Middleman` profile linked by `OneToOneField`. The `_person_create()` helper in `views.py` handles the combined Worker/Middleman + User provisioning flow.

### Entity codes

Sequential codes (`J01`, `W01`, `M01`, `C01`, `P0001`, `E001`) are generated by `_next_code(Model, prefix, pad)` in `views.py`. It reads the last record's code and increments; not atomic — avoid concurrent creates.

### Branding / AppSettings

`AppSettings` is a singleton (always `pk=1`) accessed via `AppSettings.get()`. It controls app name, logo, favicon, theme colors for light/dark mode, and login page styling. It is injected into every template as `BRANDING` by the `app_globals` context processor.

### Templates

Templates live in `templates/` (project-level, not per-app). They use Bootstrap 5 and Django template tags. The `|markdown` filter renders sanitized Markdown (used for `JobNote` bodies). Dynamic form rows (contacts, companies, addresses on the client form) use vanilla JS to add/remove rows.

### Production deployment

`docker-compose.yml` runs: PostgreSQL 16, MinIO (S3-compatible object storage), a `minio-init` one-shot container to create the bucket, and the Django app via Gunicorn. Traefik sits in front as a reverse proxy (on an external `proxy` network). The `web` service runs `migrate` and seeds the admin user on startup.
